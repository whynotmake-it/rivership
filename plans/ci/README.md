### What is concretely convoluted / broken

1. **The last mile is missing.** `tag-release.yaml:7` names its job
   `publish-packages` but it only creates tags (`tag: true`,
   tag-release.yaml:25). No publish ever happens in CI.
2. **Tags can't trigger anything.** `tag-release.yaml` checks out with the
   default `GITHUB_TOKEN` (tag-release.yaml:14-17); GitHub suppresses workflow
   runs for events created with that token, so even adding a tag-triggered
   publish workflow would silently never fire. A PAT or App token is required.
3. **No branch/mode coupling.** `version.yaml:36-38` drives
   prerelease/graduate from two independent dispatch booleans; you can dispatch
   a stable versioning run on dev or a prerelease on main. Nothing encodes
   "dev = prerelease, main = stable".
4. **Commit-message sniffing** as the release trigger:
   `if: contains(github.event.head_commit.message, 'chore(release)')`
   (tag-release.yaml:12) on both branches.
5. **Stale reference bug**: `main.yaml:54` uses
   `${{ steps.pkg.outputs.basename }}` but no step with id `pkg` exists — the
   golden-failure artifact is always named `golden-failures-`.
6. **Hand-rolled PR step**: version.yaml:41-47 pins its own
   peter-evans/create-pull-request although melos-action v3 has `create-pr`
   built in (kept deliberately — see decision D8 — but noted).

## 2. Target model

Two release trains, one shared tag→publish tail:

```
dev  (prerelease train)                      main (stable train)
────────────────────────                     ──────────────────────
feature PRs merge to dev                     PR: dev → main (when ready)
        │                                            │
workflow_dispatch "Prepare release" on dev   workflow_dispatch "Prepare release" on main
  → melos version --prerelease                 → melos version --graduate
  → publish --dry-run gate                     → publish --dry-run gate
  → PR "chore(release)" into dev               → PR "chore(release)" into main
        │ merge                                      │ merge
tag-release.yaml (PAT!) tags <pkg>-vX.Y.Z-dev.N    tags <pkg>-vX.Y.Z
        │ tag push triggers                          │ tag push triggers
publish.yaml → melos publish (OIDC) + GitHub prerelease │ → publish + GitHub release
                                                     │
                                             back-merge PR: main → dev
```

- **Branch determines mode.** The prepare workflow computes
  prerelease-vs-graduate from `github.ref_name` (dev → `--prerelease`, main →
  `--graduate`) and fails on any other branch. The two dispatch booleans go
  away.
- **Prerelease numbering**: melos `--prerelease` increments `-dev.N` per
  changed package automatically, scoped by conventional commits since each
  package's last tag — per-changed-package prereleases work without extra
  config.
- **Every stable release graduates a prerelease.** main only runs
  `--graduate`; anything that ships stable must have gone through dev and
  received a `-dev.N` first. This is what makes dev the source of truth.
  (Escape hatch for hotfixes documented in the runbook, plan 003.)
- **Publishing**: new tag-triggered `publish.yaml` using
  `bluefireteam/melos-action@v3` with `publish: true` (runs
  `melos publish -y --no-dry-run --scope=<pkg from tag>` after
  `dart-lang/setup-dart` mints the OIDC token) and `create-release: true`
  (GitHub release with the changelog section, auto-marked prerelease for
  `-dev.N` versions). Requires pub.dev "Automated publishing from GitHub
  Actions" enabled per package with tag pattern `<package>-v{{version}}` —
  admin-UI-only, maintainer action.
- **CHANGELOG flow**: melos writes prerelease entries on dev; `--graduate` on
  main rewrites to the stable version. Because main is strictly behind dev and
  the back-merge returns release commits to dev, pubspec/CHANGELOG conflicts
  don't accumulate. Release PRs are the human checkpoint for changelog quality
  (esp. motor's hand-written `## Unreleased` section — runbook covers folding
  it at graduation time).
- **`pubspec.lock` / path deps**: no inter-package path dependencies exist
  (all workspace members use `resolution: workspace` + hosted version
  constraints); heroine 0.7.2 etc. were already published from this workspace
  setup, so publishing needs no pubspec rewriting.
- **Gates before publish**: `main.yaml` already runs
  `dart analyze --fatal-infos` + full tests on every push/PR to both branches;
  the prepare workflow keeps `melos publish --dry-run` as the pre-PR gate. No
  pana gate by default (D6).

## 3. Decided defaults — maintainer to confirm

| # | Decision (default) | Alternative + one-line tradeoff |
|---|--------------------|--------------------------------|
| D1 | Prerelease suffix `-dev.N` (melos default; matches every existing prerelease tag and live pub.dev prereleases) | `-beta.N` via `--preid beta`: reads more "public", but breaks continuity with `snaptest 1.0.0-dev.3` / `stupid_simple_sheet 1.0.0-dev.2` mid-flight |
| D2 | ALL changed publishable packages ride the dev prerelease train (melos scopes by changed packages automatically) | Scope to motor only (`--scope`): fewer prerelease versions on pub.dev, but hand-maintained scope lists rot |
| D3 | Keep melos + `bluefireteam/melos-action@v3` end to end | Hand-rolled per-package `publish.yml` via `dart-lang/setup-dart` reusable workflow: less magic, but 8 workflow files + manual changelog/release plumbing |
| D4 | Human-in-the-loop release PRs (dispatch → PR → review → merge) | Fully automatic versioning on every dev push: zero-click, but noisy versions and no changelog checkpoint |
| D5 | Fine-grained PAT (contents: read/write on this repo) stored as secret `RELEASE_PAT`, used only to push tags | GitHub App installation token: no expiry babysitting, but setup overhead for a solo-maintained repo |
| D6 | No pana score gate | Add `axel-op/dart-package-analyzer` job on release PRs: catches score regressions, adds ~2 min and flakiness |
| D7 | Stable releases only by graduating prereleases (main runs `--graduate` only) | Also run plain `melos version` on main: allows direct-to-stable, but re-opens the ambiguity the split is meant to remove |
| D8 | Keep the explicit peter-evans/create-pull-request step (matches current pinning + dependabot management) | melos-action's built-in `create-pr`: one less step but generic `release-<run_id>` branch names and less control |

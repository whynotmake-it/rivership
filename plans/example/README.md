# Example App Redesign Plans

Generated by the improve skill on 2026-07-22 (audit of `packages/motor/example`,
at commit `93af2da`). This is a separate plan set from `plans/*.md` (the motor
package audit) — numbering restarts at 001 inside this directory.

**The thesis every plan serves** (maintainer's words, condensed): motor's moat
is orchestrating motion on multiple tracks — complex animation timelines — AND
responding to user input with velocity continuity, and combining the two
intuitively. Every example must explain one concept, and reading its code must
give an intuitive understanding of how motor is used. No "random animations
not driven by anything" (the old Now Playing page is the named anti-pattern).

## Target structure of the redesigned app

- **Arc 1 — Feel the difference** (recurring bottom-sheet artifact, pages 1–3;
  photo flick-dismiss for 2D): instant vs. animated → curve trap + spring
  escape → spring character + gesture velocity → more than one dimension.
- **Arc 2 — Tracks** (the missing middle): meet tracks → timelines & steps &
  loop modes (with the timeline-lanes widget) → sync barriers (payoff: Payment
  Success) → phases (payoff: Card Stack).
- **Arc 3 — Gestures × timelines** (the moat): Toggle (kept), Pull to Refresh
  (kept), Card Stack (kept), Payment Success (kept), new flagship
  boarding-pass entrance.
- **Recipes**: Snap Carousel, Toast, Picture in Picture, Draggable Icons
  (all kept).
- **Killed pages**: Why Motion, Curve Trap, The Spring, Carry the Momentum,
  Motion Character, Two Dimensions (replaced by Arc 1); Now Playing,
  Thermostat, Title Slide, Loaders, Drawer, Accordion (killed outright; the
  loaders' stagger/loop ideas and title-slide letter stagger migrate into
  Arc 2 page 6 and the flagship).

## Dependency notes

- **003 and 004 require 001**: both dock the `TimelineLanes` widget
  (Arc 2 page "Timelines & steps"; the flagship's docked lanes).
- **002 is independent** of 001 (Arc 1 uses the existing `TrajectoryLine`
  graph, not lanes) and can run in parallel with it.
- **005 runs last of the page plans**: it deletes killed pages, rewrites the
  home grid/cards, and renumbers the smoke test — doing that before 002–004
  land would break their route/card assumptions. 002/003/004 only APPEND
  routes and pages; 005 owns the final `main.dart` shape.
- **006 is independent** (touches only kept pages: toggle, pull_to_refresh,
  card_stack, payment_success) but should rebase after 005 to avoid trivial
  main.dart conflicts.
- Suggested stack order: 001 → 002 → 003 → 004 → 005 → 006.

## Executor environment notes (learned the hard way in the previous plan set)

- Work in an isolated jj/git worktree. NEVER run `git reset`/`git checkout`
  in the maintainer's main checkout.
- The workspace `pubspec.lock` is untracked. After creating a worktree, copy
  the maintainer's `/Users/tim/Developer/rivership/pubspec.lock` into the
  worktree root BEFORE `flutter pub get`, or you'll resolve `equatable 2.1.0`
  and `dart analyze --fatal-infos` will fail on deprecations that are not
  yours.
- The analyzer gate is `dart analyze --fatal-infos` (exit 0, "No issues
  found!") — infos are fatal in this repo.
